# 接口、游戏技能与模型接入规划

日期：2026 年 10 月 16 日。本文承接[内容实施方案](../AI增强实施方案-2026-10-16.md)，将接口、游戏内 skill、提示词和接入体验拆成可逐步交付的任务。初步实现范围及实际检查结果以同目录[实现报告](初步实现报告-2026-10-16.md)为准，不能将下文的后续设计视为已上线。

## 1. 接入路径与玩家操作

初版采用“选择服务商 → 填模型 ID 和 Key → 测试当前草稿 → 保存并启用”。服务商默认带入地址和协议；自定义服务或不同地域的用户可展开更多接口设置，覆盖地址和协议。所有服务商都允许手填模型 ID，不用等待代码更新才能接入新模型。预设模型只是填写示例，不代表账户有权限或永久免费。

测试必须走真实业务相同的事件文案契约，不能收到 HTTP 200 或一个“OK”就认定可用。测试不创建角色、不改变游戏存档、不保存草稿；编辑任何字段后，旧结果失效。面板应区分当前生效配置和未保存草稿，避免“填过就以为已经启用”。

本地 Ollama、LM Studio 走本机 OpenAI 兼容地址，实际模型须已下载、加载并启动服务。本机 loopback 可留空密钥；远程服务要求独立凭证。默认 Key 只保存在标签页会话，主动勾选后才长期保存在当前浏览器；旧版长期保存的 Key 提示迁移。地址中不接收 Key，界面明确请求目标，切换服务商清空旧 Key。

本轮先增加常用服务商预设和三类协议，不增加服务商账号注册、自动购额、共享密钥或默认付费服务。真实接口是否可用还受到账号、网络、跨域和服务端设置影响，协议适配测试不能代替实际接入测试。

## 2. 统一接口层

调用链拟固定为：

```text
游戏 handler → 本地确定结果 → 游戏 skill 输入投影
→ 内置提示词 → 请求协调器 → 协议适配器
→ 文本提取 → skill 输出校验 → 展示文字
```

| 协议 | 需要适配的差异 | 初版策略 |
| --- | --- | --- |
| OpenAI 兼容 Chat Completions | messages、Bearer、token 参数及 content 文本块 | 保留通用兼容层，官方 OpenAI 使用对应 token 字段；不强制所有服务支持 JSON mode |
| Anthropic Messages | 独立 system、版本头、content 文本块 | 使用原生 Messages 结构；不自动添加放宽浏览器保护的请求头 |
| Gemini generateContent | contents、systemInstruction、输出上限、候选及使用量字段 | 使用原生结构，Key 放请求头，地址按当前模型构造 |

字段与请求格式依据 [OpenAI Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)、[Anthropic Messages](https://platform.claude.com/docs/en/api/messages/create) 和 [Gemini generateContent](https://ai.google.dev/api/generate-content) 官方说明核对。使用现有兼容接口是增量改造选择；OpenAI Responses、Gemini Interactions 等新接口留作后续单独适配，不混入兼容层冒充同一协议。

地址解析集中一处：标准 Base URL 补齐路径，完整接口不重复拼接，旧自定义代理路径保留；Gemini 完整地址切换模型时同步替换末端模型。拒绝非 HTTP(S)、远端明文 HTTP、URL 内凭证及密钥参数。错误只返回应用定义的信息，不直接显示服务商响应原文、Key 或完整敏感 URL。

初版采用 12 秒总超时，覆盖请求及读取响应；支持主动取消、拒绝和截断检测、响应大小上限。并发上限为 1，忙时直接使用本地文案，不排队、不自动重试，避免自动玩法产生积压。原总方案中“最多排队 2”的可选初值延后，先采用更简单的零队列实现。

## 3. 把哪些功能做成游戏内 skill

这里的 skill 是游戏内可复用能力，不是安装到 Codex 的系统技能，也不是让模型任意执行代码。每个能力都声明 ID、输入投影、输出契约、提示词版本、请求预算和本地回退。模型不能自行选择高权限工具；现阶段由游戏调用指定能力。

| 能力 ID | 输入与输出 | 状态 / 权限 |
| --- | --- | --- |
| `adventure` | 本地故事、已定结果、学部命格 → `{story}` | 首批实现；只写展示文字 |
| `breakthrough` | 目标阶段与已定成功结果 → `{text}` | 首批实现；不计算升学成功率 |
| `enemy-name` | 学阶、挑战类型 → `{name,title}` | 首批实现；不改对手属性或建立永久人物 |
| `choice-event` | 已定事件计划、选项 ID → 正文及选项标签 | P1；仅表达白名单选项，规则引擎结算 |
| `project-continuation` | 已提交阶段与分支事实 → 下一阶段场景 | P1；程序决定是否解锁下一阶段 |
| `growth-review` | 已提交事实集合 → 带事实引用的回顾 | P2；只读，不授奖 |
| `roommate-dialogue` | 绑定室友、项目状态与有限话题 → 对白 | P2；不凭对白修改关系 |
| `build-explainer` | 已审计的装备、课程及公式计算结果 → 解释与建议 | 后续；只能解释程序预先算出的比较，不自动买卖或配装 |

新增 skill 的顺序是：定义类型与契约 → 加入本地回退 → 编写输入投影 → 编写提示词 → 加入合法、越权、长度、取消测试 → 接入指定 handler。注册表存在一项能力，不等于已经实现该能力对应的游戏流程。

暂不接受玩家上传任意脚本、远程可执行 skill 包，或模型要求增加工具权限。后续如支持内容包，首选版本化的纯数据事件配置：限定触发器、选项和本地效果 ID，校验后加载，禁止动态执行代码。

## 4. 内置提示词如何维护

提示词从原来分散在长函数中的文本，集中为四层：虚构校园背景、克制的手记文风、能力约束、JSON 输出契约。玩家姓名、历史文本等内容始终作为数据，不能覆盖上层规则。

`features/ai/skills.ts` 是首批三个能力的单一入口，包含 `promptVersion`、`outputContract`、温度和 token 上限。当前上限分别为故事 800、升学 160、名称 20/称号 30 个 Unicode 码点。解析器只接受完整 JSON 或完整围栏，不修补 `+8`、不从说明文字中截取局部对象；额外的奖励、道具、属性字段直接拒绝。

事件提示先提供本地故事及结果投影，再提供学部、命格和地点；不发送姓名 UID、完整背包、全量日志或配置 Key。升学和名称能力只发送各自必要字段。模型仍可能在语义上编造，因此生成文字不能被反向解析成奖励或人物记忆；P2 回顾还需事实引用校验。

提示词改动须递增版本并重放固定样本。首版不提供玩家直接覆盖系统提示词的入口；以后可开放文风、正文长度等受限选项，基础规则和输出契约保持不可覆盖。

## 5. 常见模型的适配策略

服务商预设覆盖硅基流动、DeepSeek、MiniMax、OpenAI、豆包、通义千问、Kimi、智谱、Gemini、Claude，以及 Ollama、LM Studio 和自定义服务。每个预设携带官方说明地址；实际可用模型以账户控制台和本地加载列表为准。

同为 OpenAI 兼容协议，也可能有温度限制、推理开关、不同 token 字段、结构化输出和流式差异。首版只发送单次文本请求所需参数，已知不支持温度的预设省略温度；不通过失败后无限更换参数来“碰运气”。推理模型若在总预算内没有最终文字，应明确失败并本地回退，不能把思考过程当作剧情。

后续能力档案按“协议 + 模型/部署 ID”记录验证结果，包括：普通文本、受限 JSON、token 参数、温度策略、平均使用量、p50/p95 延迟和最后验证日期。未经真实验证仅标“预设/协议适配”，不能标“该模型已兼容”。

下一步可增加玩家主动点击的“读取模型列表”，默认不请求、不发送跨服务商 Key；保留手填路径。地域地址、编码套餐专用端点和代理能力需要分开说明。Ollama 与 LM Studio 的兼容范围分别参照其[官方兼容说明](https://docs.ollama.com/api/openai-compatibility)和[官方端点说明](https://lmstudio.ai/docs/developer/openai-compat)。

## 6. 后续服务端 API 与运维边界

面向公开玩家提供默认 AI 时，再新增专用应用接口，例如 `POST /api/game-ai/v1/invoke`。这是拟议路径，目前不存在；不与排行榜或 UID 接口混为一谈。

建议请求只含 `skillId`、客户端请求标识和受限上下文，服务器选择允许的提示词版本、模型及输出预算；服务端不接受任意外部 URL，也不让客户端索要内部 Key。鉴权、速率限制、每日额度、请求大小、取消和脱敏日志共同实施。模型调用成功仍不代表游戏奖励提交成功，游戏结果继续由规则引擎管理。

后续交付顺序：接入基础和三项技能 → 存档单次提交与剧情闭环 → 事实回顾 → 模型能力档案及列表发现 → 有明确部署需求后提供服务端代理。每一步都保留完整本地路径。

## 7. 完成条件

第一批应通过：三协议的模拟请求与文本解析、空 200/拒绝/截断/超时/取消、旧配置和自定义模型、会话与长期密钥保存、错误脱敏、同种子在线离线同收益、上下文变化后的迟到请求拒绝。

浏览器操作和真实模型调用另列验收，缺少环境或凭证时明确标为未验证。分支剧情、持久记忆、公共代理及全存档原子结算仍依赖后续里程碑，不能用接口层测试通过替代。
