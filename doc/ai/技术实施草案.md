# AI 增强技术实施草案

状态：草案，待评审。日期：2026 年 10 月 16 日。本文只描述拟议实现；协议、目录、参数均未落地，目标参数不是实测结果。保留现有本地模板和规则的数值基线；停止采用模型自由奖励是本方案拟议的行为变化，不能承诺与旧版每次任意模型奖励完全相同。31 项审计问题另轨处理，不能以本方案已覆盖代替修复证据。

## 边界与模块

程序决定事件类型、候选 choice ID、费用、前置条件、奖励预算和最终效果；模型只能为已选计划生成受限叙事、标题及选项文案。模型返回的经验、物品、好感或任务完成字段一律拒绝，不能经旧 `AdventureResult` 直通结算。费用和收益的 canonical 数据完全在本地预置；随机结果在计划建立时固定并保存，离线、失败、重试均复用同一计划，不重新 roll。

沿用 `App → views/*Handlers → services/utils`，由 `hooks/useGameState` 组合新模块，保留 `features/save` 与 `features/modal` 已有职责；不接入其他旧 features Hook，也不更换状态库。以下均为拟新增或调整：

```text
features/narrative/
  contracts.ts / validate.ts    领域协议、运行时校验
  eventPlanner.ts              本地计划、预算、随机结果
  eventMachine.ts              状态转换与幂等纯结算
  memory.ts                    有界事实与上下文投影
  useNarrativeEvents.ts         React 编排、自动模式暂停
services/ai/
  requestCoordinator.ts        超时、取消、队列、请求身份
  narrativeRenderer.ts         生成及本地模板适配
features/save/
  saveCodec.ts                 可选扩展编解码
  saveRepository.ts            单写者、revision、持久化提交
components/NarrativeEventPanel.tsx
```

`features/modal` 仅控制面板开关，关闭面板不能等同取消计划或领取奖励。计划、ledger 和记忆归领域状态，禁止散落在弹窗局部 state。

## P0：先建立可信请求边界

先为三类 AI 调用统一输入 DTO 和输出运行时校验。网络响应使用 `unknown`，检查对象结构、字符串长度、数组上限、枚举及选项 ID 集合，拒绝未知效果字段；TypeScript 断言不算校验。上下文仅投影学部、命格、学阶、指定地点和有限事实，不发送 Key、完整存档或全部日志。

协调器统一 `AbortController`、超时、并发、去重、错误分类和降级。拟定并发上限 1、排队上限 2、单次请求超时 12 秒、文本上限 800 字符；不自动无限重试。12 秒只限制网络等待，不是剧情内容有效期。主动取消只结束请求，超时或协议错误才用本地文案；输出超限不通过截断保留半个结构。关 AI 后仍用原计划本地呈现。配置变更递增请求代次，旧配置响应不得覆盖新结果。

P0 接入时先把现有本地模板和规则的收益转为本地计划，回归核对这条基线的随机顺序及数值，再令模型补文案；不得临时把自由数值从旧响应搬入 canonical 计划。移除旧模型自由定奖须单独验收和说明，不能列作无行为变化重构。校验失败返回本地同计划文案，而非补跑一次原有随机事件。

## P1：事件状态与一次结算

拟定协议示意，省略校验器和具体本地类型；`OutcomeId` 对应程序预置效果，不能由模型创建：

```ts
type NarrativeText = {
  story: string;
  choices: { id: string; label: string }[];
};
type NarrativeEvent = {
  id: string; actionId: string; epoch: string; revision: number;
  status: 'preparing' | 'awaiting_choice' | 'submitting'
    | 'settled' | 'expired';
  planId: string; seed: string;
  options: { id: string; outcomeId: OutcomeId }[];
  text?: NarrativeText; selectedChoiceId?: string;
};
type NarrativeExtension = {
  schemaVersion: 1; revision: number; runId: string;
  pending?: NarrativeEvent;
  ledger: Settlement[]; memory: FactMemory;
};
type ExtendedGameSave = GameSave & {
  narrative?: NarrativeExtension;
};
```

状态为“准备 → 等待选择 → 提交 → 已结算”，准备或等待可因上下文撤销进入“失效”。准备时先检查资源并固定全部选项的费用与收益；把计划写入存档后才请求文案。等待时展示本地白名单选项，模型不能增加或删除 choice ID；提交时由程序按 ID 找 canonical 结果，再校验当前资源和生命周期条件。没有 choice 的现有事件使用内部确认 ID 走同一路径。

```text
创建 actionId/eventId → 固定并保存计划 → 请求文本或本地降级
→ 身份检查通过 → 等待选择 → 提交锁
→ 从最新 GameSave 校验 → 计算 nextSave
→ 一次写入 → 发布已结算状态与日志
```

请求闭包绑定 `epoch + eventId + requestId + 事件 revision`，返回时逐项匹配；模型回传身份值不可信。epoch 在导入、读档、新开、重生、退学删档等切换时更新，由本机产生，不能沿用导入值；可恢复的待选计划以原 ID 绑定新 epoch，不能复用旧请求。存档全局 revision 另用于结算 CAS：读取最新快照、核对预期 revision、纯计算后递增写入。若仅原有回血 tick 改变状态，可重读并重验后合并；资源暂缺返回等待，角色、项目阶段或关键前置失效才作废，不能沿用旧闭包覆写玩家。

所有玩家变更须通过同一提交入口排序，不能只给新剧情加锁。localStorage 没有跨标签页 CAS；拟用 Web Locks 保证新版客户端同存档单写者，未持锁页面只读。环境不支持时暂不启用剧情结算，不能声称仅比较 revision 就解决多标签并发；不配合锁的旧客户端仍属下述降级边界。

`actionId` 是唯一结算键，采用 `runId + actionSeq`；`eventId` 标识其固定剧情计划，重试不能为同一 action 新建计划。重复点击共享一次提交；ledger 已有该 action 即返回既有结果，不再扣费或发奖。原 handler 的 action 结算迁入单一提交入口：同一行动只能由旧通道或新通道之一负责。若计划包装已结束的战斗，它只能叙述既有结果，禁止追加第二份基础奖励；新剧情也不得默认叠加原 action 收益。计划没有真实时间有效期，阅读、离线和请求超时不使内容过期。只有角色、项目阶段或关键前置失效才作废；资源暂缺时保留原计划，允许稍后补足资源继续，不能重抽收益。

## 持久化与生命周期

继续使用版本 2 与原存档 key，仅增加可选 `narrative.schemaVersion=1`；旧档缺省为空记忆、空 ledger、无待选事件。一次 `GameSave` 写入须同时包含 player、logs、剧情状态、ledger 和事实记忆，禁止奖励、标记、记忆拆多个 key。提交前构造完整 nextSave，同步 `setItem` 成功后才发布成功 UI；配额不足、序列化或存储失败均保留未结算状态和错误，不先改内存假报领取成功。

自动保存、手动保存、导入导出共用完整快照并经过同一写入口；取消旧防抖任务，防止旧快照覆盖新 ledger。剧情提交属于显式保存，自动保存关闭不应使已领取奖励只存在内存，需在界面说明。导入先校验整包再替换；扩展损坏或不支持时保留原包并提示，不能静默清 ledger 后继续领取。

旧客户端仍可能读取版本 2，却在再次保存时丢弃扩展。该降级不保证剧情或幂等连续性，现有旧客户端无法靠新字段自行阻止。重新进入新客户端时缺扩展按兼容空状态开始、废弃旧待选计划，不补发历史奖励；需要跨版本完整保护时必须另议版本升级，不能宣称本扩展已经解决。

| 边界 | 拟定处理 |
| --- | --- |
| 导入、读档、新建、退学删档 | 先暂停自动模式、取消请求和旧保存任务，更新 epoch；导入失败不替换现存档；已删除角色不得被迟到响应恢复 |
| 延毕、重生 | 在降级或继续前失效旧待选计划；保留同角色已结算 ledger，重生不再次领奖；新建角色另建 runId |
| 卸载、刷新 | 作废 epoch、取消订阅与请求；下次读取持久化计划，准备中改用本地同计划；提交中若 ledger 已存在则恢复已结算，否则回到等待原选择，绝不重新 roll |
| AI 开关、模型或 Key 变化 | 取消旧请求、递增请求代次，同事件改本地文案或显式重试；不改变预算与 choice ID |
| 重复点击、旧响应 | 提交锁与幂等键拦截；身份不匹配直接丢弃，不能产生副作用 |
| 自动模式 | 准备/等待/提交时暂停自动自习和冲刺并取消已排定 timer；等待选择不自动代选，完成后由玩家恢复；现有回血按最新快照合并 |

## P2：有界事实记忆

先保存程序可证明的事实：创建时学部与命格、已结算选择、项目阶段和受控关系变化。每条记录带 fact ID、来源 eventId、时间与适用角色。模型生成的回忆只能展示，不能反写“已经获奖”“室友欠我物品”等事实。拟保留最近 24 个事件、最多 64 条事实及 16 个关系条目；重要阶段固定保留，其余按优先级淘汰。幂等归档按每个 runId 保存单调 actionSeq 水位，只有连续、已持久化结算或失效的序号才推进；高于水位的记录和未解决缺口继续保留，任何不高于水位的提交一律拒绝重结算。水位与玩家、剧情同包写入，不以清空账本或重新 roll 事件代替失败恢复。摘要丢失时从事实重建，不触碰数值。

## 渐进接入、依赖与风险

依赖顺序拟为：本地计划与收益审计 → P0 DTO/协调器/模板 → 完整快照写入口与幂等测试 → P1 状态机和面板 → P2 事实投影。先迁移升级短句和对手命名，其输入结果已由规则决定；再迁移非战斗事件，最后单独评审可选分支。阶段开关按 action 选择通道；关闭新通道时保留现有本地规则基线，开启后的奖励约束变化另列验收，不能回退到自由定奖来宣称兼容。

验收拟覆盖同计划在线/离线同收益、篡改 choice ID、重复提交、迟到响应、切角色、全部生命周期边界、存储失败、崩溃恢复、双标签和旧客户端降级。使用可注入时钟、随机源与存储，测试无真实模型费用。主要风险是旧 handler 的分散 setPlayer 与副作用、长提示词延迟、同版本降级丢扩展及账本膨胀；上述风险未完成验证前，不标注“已支持持久剧情”或“已保证一次结算”。
